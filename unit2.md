# Compiler Design Parsing: A Deep Study Guide

## 1. Introduction to Parsing

Parsing is the compiler phase that checks whether a sequence of tokens follows the grammatical rules of a programming language. A lexer first converts raw source code into tokens such as `id`, `num`, `if`, `else`, `+`, `*`, `(`, and `)`. The parser then studies this token stream and decides whether the tokens form a valid syntactic structure.

For example, if the input program contains:

```text
a + b * c
```

the lexer may produce:

```text
id + id * id
```

The parser does not care that the identifiers were originally named `a`, `b`, and `c`. It cares about whether the token pattern `id + id * id` is a legal expression according to the grammar of the language.

### 1.1 Why Parsing Exists

Programming languages have rules. An assignment statement may need an identifier on the left, an assignment symbol in the middle, and an expression on the right. An `if` statement may require a condition and a statement body. Expressions need rules for operators, operands, precedence, and grouping.

Without parsing, a compiler would only know that individual words and symbols are valid tokens. It would not know whether those tokens are arranged correctly. Parsing gives the compiler structure.

Consider:

```text
x = y + z
```

This is syntactically meaningful. But:

```text
= x y z
```

contains many of the same tokens, yet the arrangement is wrong. The parser detects this.

### 1.2 Parsing as Structure Recognition

The notes say:

> The steps to generate a string from a grammar to a string is called parsing.

This needs correction. More accurately:

> Parsing is the process of determining whether an input string can be generated by a grammar, and if so, constructing its syntactic structure.

The distinction matters. A grammar generates strings in theory. A parser receives a string and works backward or forward to verify that the grammar could have generated it.

There are two broad views:

1. Derivation view: Start from the start symbol and derive the input string.
2. Reduction view: Start from the input string and reduce it back to the start symbol.

Top-down parsers follow the first idea. Bottom-up parsers follow the second idea.

### 1.3 Grammar, Tokens, and Sentences

A context-free grammar has:

1. Terminals: actual token symbols such as `id`, `+`, `*`, `(`, `)`.
2. Nonterminals: syntactic categories such as `E`, `T`, `F`, `S`.
3. Productions: rules such as `E -> E + T`.
4. Start symbol: the main nonterminal from which complete strings are generated.

For expression grammars, common nonterminals are:

```text
E = expression
T = term
F = factor
```

The grammar:

```text
E -> E + T | T
T -> T * F | F
F -> (E) | id
```

generates expressions like:

```text
id
id + id
id * id
id + id * id
(id + id) * id
```

### 1.4 Parse Tree and Derivation

A derivation is a sequence of grammar-rule applications. A parse tree is a tree-shaped representation of the same syntactic structure.

For:

```text
E -> E + T | T
T -> F
F -> id
```

the string:

```text
id + id
```

can be derived as:

```text
E
=> E + T
=> T + T
=> F + T
=> id + T
=> id + F
=> id + id
```

This is a leftmost derivation because at every step the leftmost nonterminal is expanded first.

A rightmost derivation expands the rightmost nonterminal first:

```text
E
=> E + T
=> E + F
=> E + id
=> T + id
=> F + id
=> id + id
```

Both describe the same final string. If the grammar is unambiguous, they correspond to one parse tree.

## 2. Ambiguous Grammar

### 2.1 Simple Intuition

A grammar is ambiguous when it allows the same input string to have more than one valid structure. The problem is not that the string is invalid. The problem is that it is valid in more than one way.

Imagine a sentence:

```text
old men and women
```

Does `old` describe both men and women, or only men? Natural language often allows this kind of ambiguity. Programming languages should avoid it because compilers must make precise decisions.

In compiler design, ambiguity is especially dangerous in expression grammars. For example:

```text
id + id * id
```

should mean:

```text
id + (id * id)
```

because multiplication has higher precedence than addition. But a bad grammar may also allow:

```text
(id + id) * id
```

That changes the meaning.

### 2.2 Technical Definition

A context-free grammar is ambiguous if there exists at least one string in the language generated by the grammar that has:

1. More than one parse tree, or
2. More than one leftmost derivation, or
3. More than one rightmost derivation.

The notes say:

> If a grammar contains the same string with 2 LMD and 2 RMD for same string it is ambiguous.

This should be corrected slightly:

> A grammar is ambiguous if at least one string has two or more distinct parse trees. Equivalently, that string has two or more leftmost derivations, or two or more rightmost derivations.

You do not need to show both two leftmost derivations and two rightmost derivations. Showing either two parse trees, two leftmost derivations, or two rightmost derivations is enough.

### 2.3 Example of Ambiguous Grammar

The notes give:

```text
E -> E + E | E * E | id
w = id + id * id
```

This grammar says:

1. An expression can be expression plus expression.
2. An expression can be expression times expression.
3. An expression can be an identifier.

At first glance this looks natural, but it does not define precedence or associativity. It treats `+` and `*` equally. Therefore `id + id * id` has two meanings.

### 2.4 First Parse: Addition at the Root

We derive:

```text
id + id * id
```

as:

```text
E
=> E + E
=> id + E
=> id + E * E
=> id + id * E
=> id + id * id
```

Here the root operation is `+`. The right child is `id * id`.

So the structure is:

```text
        E
      / | \
     E  +  E
     |    / | \
    id   E  *  E
         |     |
        id    id
```

This means:

```text
id + (id * id)
```

### 2.5 Second Parse: Multiplication at the Root

Now derive the same string as:

```text
E
=> E * E
=> E + E * E
=> id + E * E
=> id + id * E
=> id + id * id
```

Here the root operation is `*`. The left child is `id + id`.

The parse tree is:

```text
        E
      / | \
     E  *  E
   / | \   |
  E  +  E id
  |     |
 id    id
```

This means:

```text
(id + id) * id
```

The same string has two parse trees, so the grammar is ambiguous.

### 2.6 Why Ambiguity Matters

Ambiguity matters because compilers must generate one meaning. In arithmetic expressions, ambiguity can change the value.

If:

```text
2 + 3 * 4
```

is parsed as:

```text
2 + (3 * 4) = 14
```

but another parse gives:

```text
(2 + 3) * 4 = 20
```

then the language definition is unclear. A compiler cannot randomly choose one parse. The grammar must encode the intended rules.

### 2.7 Converting the Ambiguous Grammar to an Unambiguous Grammar

The ambiguous grammar is:

```text
E -> E + E | E * E | id
```

We want the usual arithmetic rules:

1. Multiplication has higher precedence than addition.
2. Addition and multiplication are usually left associative.

To encode precedence, we introduce grammar levels:

```text
E -> E + T | T
T -> T * F | F
F -> id
```

Here:

1. `E` handles addition.
2. `T` handles multiplication.
3. `F` handles basic factors.

Because `E` can combine `T` using `+`, addition is at the outer level. Because `T` can combine `F` using `*`, multiplication must be completed before it becomes a `T` used in addition.

### 2.8 Deriving `id + id * id` in the Unambiguous Grammar

Use:

```text
E -> E + T | T
T -> T * F | F
F -> id
```

Leftmost derivation:

```text
E
=> E + T
=> T + T
=> F + T
=> id + T
=> id + T * F
=> id + F * F
=> id + id * F
=> id + id * id
```

The parse tree is:

```text
        E
      / | \
     E  +  T
     |    / | \
     T   T  *  F
     |   |     |
     F   F    id
     |   |
    id  id
```

This forces:

```text
id + (id * id)
```

There is no parse tree for:

```text
(id + id) * id
```

because multiplication is handled inside `T`, and `T` cannot directly contain an `E + T` on its left unless parentheses are introduced through `F -> (E)`.

### 2.9 Adding Parentheses

A practical expression grammar usually includes parentheses:

```text
E -> E + T | T
T -> T * F | F
F -> (E) | id
```

Now:

```text
(id + id) * id
```

is allowed, but only because parentheses explicitly request that grouping.

### 2.10 Common Mistakes About Ambiguity

Students often think a grammar is ambiguous because it has multiple productions for one nonterminal. That is not necessarily true. For example:

```text
S -> aS | b
```

has alternatives, but each valid string has only one parse.

Another mistake is thinking ambiguity belongs to the string, not the grammar. A string may be ambiguous with respect to one grammar and unambiguous with respect to another. Ambiguity is a property of a grammar.

A third mistake is assuming precedence is automatically understood. Grammars do not know arithmetic conventions unless those conventions are encoded in the grammar or handled separately by parser declarations.

## 3. Left Recursion

### 3.1 Simple Intuition

A grammar is left recursive when a nonterminal can eventually call itself as the first symbol on the right-hand side. This is a problem for top-down parsers because the parser may keep calling the same procedure without consuming input.

Suppose:

```text
E -> E + T | T
```

If a recursive descent parser tries to parse `E`, it may choose `E -> E + T`. To parse that, it must first parse `E` again. That new call may again choose `E -> E + T`, and so on forever.

The parser gets stuck before reading any input.

### 3.2 Technical Definition

A grammar is immediately left recursive if it has a production:

```text
A -> A α
```

where `α` is any sequence of grammar symbols.

It is indirectly left recursive if:

```text
A =>+ A α
```

through multiple derivation steps.

Example of immediate left recursion:

```text
E -> E + T | T
```

Example of indirect left recursion:

```text
A -> B a
B -> A b | c
```

Here:

```text
A => B a => A b a
```

So `A` eventually derives a string beginning with `A`.

### 3.3 Why Left Recursion Matters

Left recursion is not always bad. Bottom-up parsers such as LR parsers handle left recursion naturally and often prefer it because it represents left associativity efficiently.

However, top-down parsers, especially recursive descent and LL parsers, cannot handle left-recursive grammars directly. Therefore left recursion must be removed before constructing a predictive parser.

### 3.4 Standard Elimination Formula

The notes give:

```text
A -> A α | β

A -> β A'
A' -> ε | α A'
```

The usual order is often written as:

```text
A  -> β A'
A' -> α A' | ε
```

Both are equivalent. The new nonterminal `A'` represents “zero or more repetitions of `α` after `β`.”

### 3.5 Why the Formula Works

Original grammar:

```text
A -> A α | β
```

This can produce:

```text
β
β α
β α α
β α α α
...
```

The transformed grammar:

```text
A  -> β A'
A' -> α A' | ε
```

also produces:

```text
A => β A' => β
A => β A' => β α A' => β α
A => β A' => β α A' => β α α A' => β α α
```

The language is preserved, but the recursion moves to the right.

### 3.6 Example: `E -> E - T | T`

Original:

```text
E -> E - T | T
```

Here:

```text
A = E
α = - T
β = T
```

After elimination:

```text
E  -> T E'
E' -> - T E' | ε
```

This grammar generates:

```text
T
T - T
T - T - T
```

For input:

```text
id - id - id
```

the grammar derives:

```text
E
=> T E'
=> id E'
=> id - T E'
=> id - id E'
=> id - id - T E'
=> id - id - id E'
=> id - id - id
```

### 3.7 Multiple Left-Recursive Alternatives

The notes ask for examples where a nonterminal has more than two alternatives.

General form:

```text
A -> A α1 | A α2 | ... | A αm | β1 | β2 | ... | βn
```

where:

1. `A α1`, `A α2`, ..., `A αm` are left-recursive alternatives.
2. `β1`, `β2`, ..., `βn` are non-left-recursive alternatives.

Transformation:

```text
A  -> β1 A' | β2 A' | ... | βn A'
A' -> α1 A' | α2 A' | ... | αm A' | ε
```

Example:

```text
S -> S a b | S c d | a | b | c
```

Left-recursive parts:

```text
S a b
S c d
```

So:

```text
α1 = ab
α2 = cd
```

Non-left-recursive parts:

```text
a
b
c
```

So:

```text
β1 = a
β2 = b
β3 = c
```

Eliminated grammar:

```text
S  -> a S' | b S' | c S'
S' -> ab S' | cd S' | ε
```

This generates strings such as:

```text
a
b
c
aab
bcd
cabcd
```

### 3.8 Solving Given Left Recursion Examples

#### Example 1

```text
S -> S d a | c a | b
```

Left-recursive alternative:

```text
S d a
```

Non-left-recursive alternatives:

```text
c a
b
```

Result:

```text
S  -> ca S' | b S'
S' -> da S' | ε
```

#### Example 2

```text
E -> E - T | T
```

Result:

```text
E  -> T E'
E' -> - T E' | ε
```

#### Example 3

```text
A -> S d | c
```

This is not immediately left recursive in `A`, because the right-hand side does not begin with `A`. It may be indirectly left recursive only if `S` can derive something beginning with `A`. Without such information, no immediate left-recursion removal is needed.

#### Example 4

```text
S -> S a b | S c d | a | b | c
```

Result:

```text
S  -> a S' | b S' | c S'
S' -> ab S' | cd S' | ε
```

#### Example 5

```text
T -> T * F | F
```

Result:

```text
T  -> F T'
T' -> * F T' | ε
```

#### Example 6

```text
A -> A a | A c d | d | a
```

Left-recursive alternatives:

```text
A a
A c d
```

Non-left-recursive alternatives:

```text

a
```

Result:

```text
A  -> d A' | a A'

```

#### Example 7


### 3.9 Common Mistakes in Left Recursion

A common mistake is removing all recursion. Only left recursion is a problem for LL parsing. Right recursion is allowed.

Another mistake is treating any production containing the same nonterminal as left recursive. For example:

```text
A -> b A
```

is recursive but not left recursive. It consumes `b` before calling `A`, so recursive descent can progress.

A third mistake is forgetting multiple `β` alternatives. In:

```text
A -> A x | b | c
```

both `b` and `c` must be preserved:

```text
A  -> b A' | c A'
A' -> x A' | ε
```

## 4. Left Factoring and Non-Deterministic Grammar

### 4.1 Simple Intuition

Left factoring is needed when two or more productions begin with the same prefix. A top-down parser chooses a production by looking at the next input token. If several alternatives begin the same way, the parser cannot decide immediately.

Example:

```text
A -> α β1 | α β2
```

Both alternatives begin with `α`. If the parser sees `α`, it does not know whether the input should continue as `β1` or `β2`.

Left factoring postpones the decision until enough input has been seen.

### 4.2 Technical Explanation

General form:

```text
A -> α β1 | α β2 | α β3 | α β4
```

Factored form:

```text
A  -> α A'
A' -> β1 | β2 | β3 | β4
```

The common prefix `α` is pulled out. The parser first matches `α`, then decides among `β1`, `β2`, `β3`, and `β4`.

### 4.3 Why This Fixes Non-Determinism

The notes say:

> Generate α β4 from this, this will lead to lots of possibility so in Non deterministic grammar.

The clearer version is:

> If several alternatives begin with the same prefix, a top-down parser cannot deterministically choose one alternative using only the next input symbol. Left factoring rewrites the grammar so that the common prefix is parsed once, and the decision is delayed until the alternatives differ.

### 4.4 Example: If-Else Grammar

The classic example is the dangling-else grammar:

```text
S -> if E then S
   | if E then S else S
   | a
```

Both first two alternatives begin with:

```text
if E then S
```

Left factoring gives:

```text
S  -> if E then S S' | a
S' -> else S | ε
```

This grammar still has the dangling-else ambiguity unless language rules specify that `else` binds to the nearest unmatched `if`. Left factoring alone solves the immediate predictive-choice problem, but it does not always remove ambiguity.

### 4.5 Example: Function Call or Variable

Suppose:

```text
Stmt -> id = Expr
      | id ( ArgList )
```

Both alternatives start with `id`. After seeing `id`, the parser cannot choose. Factor:

```text
Stmt  -> id Stmt'
Stmt' -> = Expr | ( ArgList )
```

Now the parser consumes `id` first. Then:

1. If the next token is `=`, it is an assignment.
2. If the next token is `(`, it is a function call.

### 4.6 Common Mistakes in Left Factoring

Students sometimes factor only one token when the common prefix is longer. For:

```text
S -> a b c | a b d | a e
```

the best factoring is:

```text
S  -> a S'
S' -> b S'' | e
S'' -> c | d
```

Another mistake is thinking left factoring changes the language. Correct left factoring preserves the language; it only changes the grammar shape.

## 5. Top-Down and Bottom-Up Parsing

### 5.1 Big Picture

The notes classify parsers as:

```text
Parser
  Top down              Bottom up
  - Recursive           - Operator precedence
  - Non Recursive       - LR(0), LR(1)
    (Predictive)        - SLR(1)
                         - CLR(1)
                         - LALR(1)
```

This classification is broadly correct, but needs refinement:

1. Recursive descent is a top-down parsing technique.
2. Predictive parsing is a top-down technique that avoids backtracking, often implemented recursively or non-recursively.
3. Operator-precedence parsing is a bottom-up method for operator grammars.
4. LR parsers are powerful bottom-up parsers.
5. CLR(1) means canonical LR(1).
6. LALR(1) means lookahead LR, commonly used in parser generators such as Yacc/Bison.

### 5.2 Top-Down Parsing Intuition

Top-down parsing starts from the start symbol and tries to derive the input. It asks:

> Can I expand the grammar from the top until I get the input tokens?

For input:

```text
id + id
```

and grammar:

```text
E -> T E'
E' -> + T E' | ε
T -> id
```

a top-down parser begins with `E`, expands it into `T E'`, matches `id`, then expands `E'` based on the next token `+`.

### 5.3 Bottom-Up Parsing Intuition

Bottom-up parsing starts from the input and tries to reduce it to the start symbol. It asks:

> Can I find pieces of the input that match the right-hand side of grammar productions and replace them with nonterminals?

For:

```text
id + id
```

with:

```text
E -> E + T | T
T -> id
```

bottom-up parsing may reduce:

```text
id + id
=> T + id
=> E + id
=> E + T
=> E
```

### 5.4 Output of a Parser

A parser may produce:

1. Parse tree.
2. Abstract syntax tree.
3. Syntax errors.
4. Intermediate data for semantic analysis.

A parse tree contains every grammar symbol, including helper nonterminals. An abstract syntax tree removes unnecessary grammar details and keeps the essential program structure.

For:

```text
id + id * id
```

a parse tree may include `E`, `T`, `F`, `E'`, and `T'`. An AST may simply be:

```text
      +
     / \
   id   *
       / \
     id  id
```

### 5.5 Top-Down Example

Grammar:

```text
E  -> T E'
E' -> + T E' | ε
T  -> id
```

Input:

```text
id + id $
```

Derivation:

```text
E
=> T E'
=> id E'
=> id + T E'
=> id + id E'
=> id + id
```

This is top-down because we start from `E` and expand toward the input.

### 5.6 Bottom-Up Example

Grammar:

```text
E -> E + T | T
T -> id
```

Input:

```text
id + id $
```

Reduction:

```text
id + id
=> T + id
=> E + id
=> E + T
=> E
```

This is bottom-up because we start from the input and reduce to the start symbol.

## 6. Recursive Descent Parsing

### 6.1 Simple Intuition

Recursive descent parsing builds one procedure for each nonterminal. If the grammar has `E`, `T`, and `F`, the parser has functions like `E()`, `T()`, and `F()`.

When a nonterminal appears in a production, the parser calls the corresponding function. When a terminal appears, the parser matches it with the current input token.

### 6.2 Requirements

The notes say:

```text
No left recursion, No left factoring
```

This should be corrected:

> For simple predictive recursive descent parsing, the grammar should have no left recursion and should be left factored.

The phrase “No left factoring” is wrong. We need left factoring, not absence of left factoring. The intended meaning was likely “no need for backtracking after left factoring.”

### 6.3 Example Grammar

The notes give:

```text
E  -> i E'
E' -> + i E' | ε
```

This grammar generates:

```text
i
i + i
i + i + i
```

Here `i` represents an identifier token.

### 6.4 Recursive Descent Pseudocode

The notes provide:

```text
E'() {
  if (input == '+') {
    input ++;
    if (input == 'i') {
      input ++;
      E'();
    }
  } else
    return;
}

E() {
  if (input == 'i') {
    input ++;
    E'();
  }
}

main() {
  E();
  if (input == '$')
    parsing successful
}
```

This is a good beginner sketch, but a real parser should report errors when expected tokens are missing.

Improved pseudocode:

```text
lookahead = nextToken()

match(token):
    if lookahead == token:
        lookahead = nextToken()
    else:
        error("expected " + token)

E():
    match(i)
    EPrime()

EPrime():
    if lookahead == '+':
        match('+')
        match(i)
        EPrime()
    else:
        return

main:
    E()
    match('$')
```

### 6.5 Parsing `i + i + i`

Input:

```text
i + i + i $
```

Call sequence:

```text
E()
  match(i)
  EPrime()
    lookahead is '+'
    match(+)
    match(i)
    EPrime()
      lookahead is '+'
      match(+)
      match(i)
      EPrime()
        lookahead is '$'
        return
```

The parser succeeds because after `E()` finishes, the lookahead is `$`.

### 6.6 Common Mistakes

One mistake is forgetting to advance the input after matching a token. If the parser checks `input == 'i'` but does not move to the next token, it may repeatedly see the same token.

Another mistake is using `else return` for all unexpected tokens. In `EPrime`, returning on `$` is correct because `E' -> ε` is valid at the end. But returning on a token such as `*` may hide an error depending on the grammar. A proper parser uses FOLLOW sets to decide when ε is allowed.

## 7. FIRST and FOLLOW Sets

### 7.1 Why FIRST and FOLLOW Exist

FIRST and FOLLOW sets help predictive parsers decide which production to use. They answer two practical questions:

1. FIRST: What terminal can appear first if I expand this symbol or string?
2. FOLLOW: What terminal can appear immediately after this nonterminal in a valid sentence?

These sets are essential for LL(1) parsing table construction.

### 7.2 FIRST Set Intuition

The notes say:

> First of A gives set of terminals that begins in all strings derived from A.

A clearer definition:

> FIRST(A) is the set of terminals that can appear as the first symbol of some string derived from `A`. If `A` can derive the empty string, then ε is also included.

The phrase “all strings” can be misleading. FIRST contains terminals that begin at least one possible string derived from the symbol.

Example:

```text
A -> aB | cD | ε
```

Then:

```text
FIRST(A) = { a, c, ε }
```

### 7.3 FOLLOW Set Intuition

The notes say:

> Follow(A) gives set of all terminals that follow immediately to right of A.

Correct and slightly expanded:

> FOLLOW(A) is the set of terminals that can appear immediately to the right of `A` in some sentential form derived from the start symbol. If `A` can appear at the end of the input, `$` is included.

For the start symbol `S`:

```text
FOLLOW(S) = { $ }
```

because `$` marks end of input.

### 7.4 FIRST Rules

Important rules:

1. If `X` is a terminal, then `FIRST(X) = {X}`.
2. If `A -> ε`, then add `ε` to `FIRST(A)`.
3. If `A -> a α`, where `a` is terminal, add `a` to `FIRST(A)`.
4. If `A -> B C`, add `FIRST(B) - {ε}` to `FIRST(A)`.
5. If `B` can derive ε, also consider `FIRST(C)`.
6. If every symbol in a right-hand side can derive ε, add ε.

The notes say:

> if A -> B C then First(A) = First(B)

This is incomplete. It is true only if `B` cannot derive ε. If `B` can derive ε, then FIRST(C) also matters.

Example:

```text
A -> B C
B -> ε | b
C -> c
```

Then:

```text
FIRST(B) = { b, ε }
FIRST(C) = { c }
FIRST(A) = { b, c }
```

Why `c`? Because `B` may disappear, leaving `C` first.

### 7.5 FOLLOW Rules

Use these rules repeatedly until no set changes:

1. Put `$` in FOLLOW(start symbol).
2. If `A -> α B β`, add `FIRST(β) - {ε}` to FOLLOW(B).
3. If `A -> α B β` and `β =>* ε`, add FOLLOW(A) to FOLLOW(B).
4. If `A -> α B`, add FOLLOW(A) to FOLLOW(B).

The notes say:

> If A -> α B β, then Follow(B) = First(β) if First(β) doesn't contain ε

This should be:

> Add `FIRST(β) - {ε}` to FOLLOW(B). If `β` can derive ε, also add FOLLOW(A) to FOLLOW(B).

We “add” because FOLLOW sets may receive symbols from many productions.

### 7.6 FIRST and FOLLOW Example

Grammar:

```text
E  -> T E'
E' -> + T E' | ε
T  -> F T'
T' -> * F T' | ε
F  -> id | ( E )
```

FIRST sets:

`F` begins with `id` or `(`:

```text
FIRST(F) = { id, ( }
```

`T -> F T'`, so:

```text
FIRST(T) = FIRST(F) = { id, ( }
```

`E -> T E'`, so:

```text
FIRST(E) = FIRST(T) = { id, ( }
```

`E' -> + T E' | ε`, so:

```text
FIRST(E') = { +, ε }
```

`T' -> * F T' | ε`, so:

```text
FIRST(T') = { *, ε }
```

FOLLOW sets:

Start symbol:

```text
FOLLOW(E) = { $, ) }
```

Why `)`? Because `F -> ( E )`, so `)` can follow `E`.

For `E -> T E'`, `E'` follows `T`, so add FIRST(E') minus ε:

```text
FOLLOW(T) includes { + }
```

Since `E'` can be ε, FOLLOW(E) also follows `T`:

```text
FOLLOW(T) = { +, $, ) }
```

For `T -> F T'`, FIRST(T') minus ε gives `*`, and since `T'` can be ε, FOLLOW(T) also follows `F`:

```text
FOLLOW(F) = { *, +, $, ) }
```

For `E -> T E'`, `E'` is at the end, so:

```text
FOLLOW(E') = FOLLOW(E) = { $, ) }
```

For `T -> F T'`, `T'` is at the end:

```text
FOLLOW(T') = FOLLOW(T) = { +, $, ) }
```

Final:

```text
FIRST(E)  = { id, ( }
FIRST(E') = { +, ε }
FIRST(T)  = { id, ( }
FIRST(T') = { *, ε }
FIRST(F)  = { id, ( }

FOLLOW(E)  = { $, ) }
FOLLOW(E') = { $, ) }
FOLLOW(T)  = { +, $, ) }
FOLLOW(T') = { +, $, ) }
FOLLOW(F)  = { *, +, $, ) }
```

## 8. LL(1) Parsing

### 8.1 Meaning of LL(1)

LL(1) means:

1. The first `L`: input is scanned from Left to right.
2. The second `L`: the parser produces a Leftmost derivation.
3. The `1`: the parser uses one lookahead token.

An LL(1) parser is predictive. It decides which production to use by looking at the current nonterminal on the stack and the next input token.

### 8.2 LL(1) Parsing Table Construction

For every production:

```text
A -> α
```

use:

1. For every terminal `a` in `FIRST(α)`, put `A -> α` in `M[A, a]`.
2. If `ε` is in `FIRST(α)`, then for every `b` in `FOLLOW(A)`, put `A -> α` in `M[A, b]`.
3. If any table cell receives more than one production, the grammar is not LL(1).

This matches the notes:

```text
1) Add A -> α under M[A, a] where a ∈ First(α)
2) Add A -> α under M[A, a] where a ∈ Follow(A) if First(α) contains ε
```

The second rule should say `a ∈ FOLLOW(A)`, not `First(α)`.

### 8.3 LL(1) Table for Expression Grammar

Grammar:

```text
E  -> T E'
E' -> + T E' | ε
T  -> F T'
T' -> * F T' | ε
F  -> id | ( E )
```

FIRST and FOLLOW:

```text
E:  FIRST { id, ( }    FOLLOW { $, ) }
E': FIRST { +, ε }     FOLLOW { $, ) }
T:  FIRST { id, ( }    FOLLOW { +, $, ) }
T': FIRST { *, ε }     FOLLOW { +, $, ) }
F:  FIRST { id, ( }    FOLLOW { +, *, $, ) }
```

Parsing table:

```text
        id        +           *          (          )          $
E       E->TE'                           E->TE'
E'                E'->+TE'                          E'->ε     E'->ε
T       T->FT'                           T->FT'
T'                T'->ε      T'->*FT'               T'->ε     T'->ε
F       F->id                            F->(E)
```

### 8.4 How the Non-Recursive LL(1) Parser Works

The parser uses a stack. Initially:

```text
Stack: $ E
Input: id + id $
```

At every step:

1. Let `X` be the top stack symbol.
2. Let `a` be the current input token.
3. If `X` is a terminal and `X == a`, pop it and advance input.
4. If `X` is a nonterminal, use table entry `M[X, a]`.
5. If the entry contains a production, pop `X` and push the right-hand side in reverse.
6. If the entry is empty, report syntax error.
7. If both stack top and input are `$`, accept.

### 8.5 Parsing `id + id $`

The notes provide the trace. Here it is cleaned and explained.

```text
Stack        Input        Action
$E           id + id $    E -> T E'
$E'T         id + id $    T -> F T'
$E'T'F       id + id $    F -> id
$E'T'id      id + id $    match id
$E'T'        + id $       T' -> ε
$E'          + id $       E' -> + T E'
$E'T+        + id $       match +
$E'T         id $         T -> F T'
$E'T'F       id $         F -> id
$E'T'id      id $         match id
$E'T'        $            T' -> ε
$E'          $            E' -> ε
$            $            accept
```

Notice why `T' -> ε` is chosen when the next token is `+`. Since `+` is in FOLLOW(T'), it means the current term has ended and the expression is moving to addition.

### 8.6 How to Check Whether a Grammar is LL(1)

A grammar is LL(1) if no parsing-table cell contains more than one production.

Equivalent conditions for every nonterminal `A` with alternatives:

```text
A -> α1 | α2 | ... | αn
```

1. `FIRST(αi)` and `FIRST(αj)` must be disjoint for all `i != j`.
2. If `ε` is in `FIRST(αi)`, then `FIRST(αj)` must be disjoint from FOLLOW(A) for every `j != i`.
3. At most one alternative should derive ε.

Practical checklist:

1. Remove left recursion.
2. Apply left factoring.
3. Compute FIRST sets.
4. Compute FOLLOW sets.
5. Build the LL(1) table.
6. Check for multiple entries in any cell.

### 8.7 LL(1) Common Mistakes

Students often think that if a grammar has no left recursion, it must be LL(1). That is false. It may still require left factoring.

Another mistake is using FOLLOW sets for every production. FOLLOW is used only when a production can derive ε.

Another mistake is forgetting `$` in FOLLOW(start symbol), causing missing accept behavior in the parser.

## 9. Recursive Descent vs Non-Recursive Predictive Parsing

Recursive descent parsing uses procedures. Non-recursive predictive parsing uses a stack and parsing table. Both are top-down and often LL(1)-based.

Recursive descent advantages:

1. Easy to write by hand.
2. Clear mapping between grammar and code.
3. Good for small languages and teaching.
4. Error messages can be customized.

Recursive descent disadvantages:

1. Left recursion must be removed.
2. Large grammars produce many procedures.
3. Backtracking versions may be inefficient.

Non-recursive predictive parsing advantages:

1. Uses a table-driven algorithm.
2. Easy to implement mechanically.
3. Good for demonstrating LL(1) parsing formally.

Disadvantages:

1. Parsing tables can be large.
2. Error messages may be less natural unless carefully designed.
3. Grammar must satisfy LL(1) restrictions.

## 10. LR Parsing and Bottom-Up Parsing

### 10.1 Simple Intuition

LR parsing is a powerful bottom-up technique. It reads input from left to right and constructs a rightmost derivation in reverse.

The name LR means:

1. `L`: scan input Left to right.
2. `R`: construct a Rightmost derivation in reverse.

Instead of expanding the start symbol, LR parsers shift input symbols onto a stack and reduce recognized patterns.

### 10.2 Shift and Reduce

The two main operations are:

1. Shift: move the next input token onto the stack.
2. Reduce: replace symbols on top of the stack matching a production right-hand side with the production left-hand side.

Example:

```text
E -> E + T | T
T -> id
```

Input:

```text
id + id $
```

Possible actions:

```text
shift id
reduce id to T
reduce T to E
shift +
shift id
reduce id to T
reduce E + T to E
accept
```

### 10.3 Handle and Handle Pruning

A handle is a substring that matches the right-hand side of a production and whose reduction represents one step in the reverse of a rightmost derivation.

Handle pruning means repeatedly finding handles and reducing them until the start symbol remains.

For:

```text
id + id * id
```

under the usual expression grammar, bottom-up parsing reduces the multiplication part first because `id * id` forms a handle at the correct time.

### 10.4 LR Parser Components

An LR parser uses:

1. Stack of states and grammar symbols.
2. Input buffer.
3. ACTION table.
4. GOTO table.

ACTION tells what to do for terminals:

1. shift
2. reduce
3. accept
4. error

GOTO tells which state to enter after reducing to a nonterminal.

## 11. LR(0) Items, Closure, and GOTO

### 11.1 LR(0) Item Intuition

An LR(0) item is a production with a dot inserted somewhere on the right-hand side. The dot shows how much of that production has already been recognized.

For:

```text
A -> a A
```

LR(0) items are:

```text
A -> . a A
A -> a . A
A -> a A .
```

Meaning:

1. `A -> . a A`: we are about to recognize `a A`.
2. `A -> a . A`: we have recognized `a`, now expect `A`.
3. `A -> a A .`: the full right-hand side has been recognized; reduce by `A -> a A`.

### 11.2 Closure

Closure adds all productions that may be needed next.

If an item contains:

```text
A -> α . B β
```

and `B` is a nonterminal, then the parser may next need to recognize a `B`. Therefore, add:

```text
B -> . γ
```

for every production `B -> γ`.

Repeat until no new items can be added.

Example from notes:

```text
S -> A A
A -> a A | b
```

Closure of:

```text
S -> . A A
```

is:

```text
S -> . A A
A -> . a A
A -> . b
```

Why? The dot is before `A`, so all ways to start `A` must be included.

### 11.3 GOTO

`GOTO(I, X)` means:

> If the parser is in item set `I` and recognizes symbol `X`, where can the dot move?

Algorithm:

1. Find all items in `I` where the dot is immediately before `X`.
2. Move the dot over `X`.
3. Take closure of the resulting items.

Example:

If:

```text
I:
S -> . A A
A -> . a A
A -> . b
```

Then:

```text
GOTO(I, A)
```

starts from:

```text
S -> A . A
```

Closure adds:

```text
A -> . a A
A -> . b
```

so:

```text
GOTO(I, A):
S -> A . A
A -> . a A
A -> . b
```

### 11.4 LR(0) Table Construction Steps

1. Augment the grammar with `S' -> S`.
2. Construct the initial item set `I0 = closure(S' -> . S)`.
3. Compute GOTO for every item set on every grammar symbol.
4. Continue until no new item sets appear.
5. Fill ACTION and GOTO tables:
   - If `A -> α . a β` and `GOTO(Ii, a) = Ij`, put `shift j` in ACTION[i, a].
   - If `A -> α .` and `A != S'`, put `reduce A -> α` in ACTION[i, a] for all terminals `a`.
   - If `S' -> S .`, put accept in ACTION[i, $].
   - If `GOTO(Ii, A) = Ij` for nonterminal `A`, put `j` in GOTO[i, A].

LR(0) uses no lookahead for reductions. That is why reductions are placed under all terminals. This makes LR(0) simple but weak.

## 12. LR(0) Worked Example: `S -> A A`, `A -> a A | b`

### 12.1 Grammar

Original:

```text
S -> A A
A -> a A | b
```

Augmented:

```text
S' -> S
S  -> A A
A  -> a A
A  -> b
```

Number productions:

```text
1: S -> A A
2: A -> a A
3: A -> b
```

### 12.2 Canonical LR(0) Item Sets

Initial:

```text
I0:
S' -> . S
S  -> . A A
A  -> . a A
A  -> . b
```

Transitions:

```text
GOTO(I0, S) = I1
I1:
S' -> S .
```

```text
GOTO(I0, A) = I2
I2:
S -> A . A
A -> . a A
A -> . b
```

```text
GOTO(I0, a) = I3
I3:
A -> a . A
A -> . a A
A -> . b
```

```text
GOTO(I0, b) = I4
I4:
A -> b .
```

From `I2`:

```text
GOTO(I2, A) = I5
I5:
S -> A A .
```

```text
GOTO(I2, a) = I3
GOTO(I2, b) = I4
```

From `I3`:

```text
GOTO(I3, A) = I6
I6:
A -> a A .
```

```text
GOTO(I3, a) = I3
GOTO(I3, b) = I4
```

### 12.3 LR(0) Parsing Table

```text
            ACTION              GOTO
       a       b       $       S      A
0      S3      S4              1      2
1                      acc
2      S3      S4                     5
3      S3      S4                     6
4      r3      r3      r3
5      r1      r1      r1
6      r2      r2      r2
```

This matches the notes.

### 12.4 Parsing `a a b b $`

The notes begin:

```text
0 a 3 a 3 b 4 A 6 A 5 ...
```

Let us complete the trace carefully.

Stack stores states and grammar symbols. We show the rightmost state as the current state.

Input:

```text
a a b b $
```

Trace:

```text
Stack              Input        Action
0                  a a b b $    ACTION[0,a] = S3
0 a 3              a b b $      ACTION[3,a] = S3
0 a 3 a 3          b b $        ACTION[3,b] = S4
0 a 3 a 3 b 4      b $          ACTION[4,b] = r3: A -> b
0 a 3 a 3 A 6      b $          GOTO[3,A] = 6
0 a 3 a 3 A 6      b $          ACTION[6,b] = r2: A -> a A
0 a 3 A 6          b $          GOTO[3,A] = 6
0 a 3 A 6          b $          ACTION[6,b] = r2: A -> a A
0 A 2              b $          GOTO[0,A] = 2
0 A 2              b $          ACTION[2,b] = S4
0 A 2 b 4          $            ACTION[4,$] = r3: A -> b
0 A 2 A 5          $            GOTO[2,A] = 5
0 A 2 A 5          $            ACTION[5,$] = r1: S -> A A
0 S 1              $            GOTO[0,S] = 1
0 S 1              $            ACTION[1,$] = accept
```

Explanation of reductions:

1. `b` is reduced to `A`.
2. `a A` is reduced to `A`.
3. Another `a A` is reduced to `A`.
4. Later `b` is reduced to `A`.
5. Finally `A A` is reduced to `S`.

So:

```text
a a b b
=> a a A b
=> a A b
=> A b
=> A A
=> S
```

## 13. SLR(1) Parsing

### 13.1 Why SLR Exists

LR(0) is too aggressive with reductions. Whenever it sees a completed item:

```text
A -> α .
```

it reduces on every terminal. But sometimes a reduction is valid only before certain lookahead symbols.

SLR(1) improves LR(0) by using FOLLOW sets.

### 13.2 SLR Reduction Rule

In LR(0):

```text
A -> α .
```

causes reduction by `A -> α` under all terminals.

In SLR(1):

```text
A -> α .
```

causes reduction only under terminals in `FOLLOW(A)`.

This reduces conflicts.

### 13.3 SLR Table Construction

1. Construct LR(0) item sets.
2. Compute FOLLOW sets.
3. Fill shift actions as in LR(0).
4. For completed item `A -> α .`, put reduce `A -> α` only in ACTION[i, a] for `a ∈ FOLLOW(A)`.
5. Put accept for `S' -> S .` on `$`.
6. Fill GOTO table for nonterminals.

### 13.4 SLR Example Using `S -> A A`

For:

```text
S -> A A
A -> a A | b
```

FOLLOW sets:

```text
FOLLOW(S) = { $ }
FOLLOW(A) = { a, b, $ }
```

Why FOLLOW(A) contains `a` and `b`? In `S -> A A`, the first `A` is followed by another `A`. Since `FIRST(A) = {a, b}`, both `a` and `b` can follow the first `A`. The second `A` is at the end of `S`, so `$` follows it.

In this example, SLR table is similar to LR(0), because FOLLOW(A) includes all terminals. But for many grammars, SLR prevents unnecessary reductions.

### 13.5 Inadequate State

An inadequate state is a parser state that contains a conflict. In LR parsing, conflicts usually mean:

1. Shift-reduce conflict: the table wants both shift and reduce in the same cell.
2. Reduce-reduce conflict: the table wants two different reductions in the same cell.

In LR(0), an inadequate state may contain:

```text
A -> α .
B -> β . a γ
```

The completed item suggests reducing. The item with dot before terminal `a` suggests shifting `a`. Since LR(0) reduces on all terminals, a conflict appears on `a`.

In SLR, the conflict may disappear if `a` is not in FOLLOW(A).

An inadequate state tells us the parser cannot make a unique decision using the information available to that parsing method.

## 14. CLR(1), or Canonical LR(1), Parsing

### 14.1 Why CLR(1) Exists

SLR uses FOLLOW sets, but FOLLOW sets are sometimes too broad. FOLLOW(A) includes every terminal that can follow `A` anywhere in the grammar, even if only a smaller set is valid in the current parser state.

CLR(1) fixes this by attaching lookahead terminals directly to LR items.

An LR(1) item has the form:

```text
[A -> α . β, a]
```

where `a` is the lookahead terminal under which this item is valid.

### 14.2 LR(1) Item Intuition

The dot tells what has been recognized. The lookahead tells when reduction is allowed.

For:

```text
[A -> α ., a]
```

the parser reduces by `A -> α` only if the next input token is `a`.

This is more precise than SLR because lookahead is state-specific.

### 14.3 LR(1) Closure

If an LR(1) item contains:

```text
[A -> α . B β, a]
```

then for every production:

```text
B -> γ
```

add:

```text
[B -> . γ, b]
```

for every:

```text
b ∈ FIRST(β a)
```

This rule is the heart of CLR parsing.

Intuition:

If we are about to parse `B`, what can appear after that `B`? It is followed by `β`, and after `β` comes the original lookahead `a`. Therefore the lookahead for `B` is FIRST of `β a`.

### 14.4 LR(1) GOTO

GOTO is similar to LR(0), but lookaheads are carried with the items.

From:

```text
[A -> α . X β, a]
```

on symbol `X`, move to:

```text
[A -> α X . β, a]
```

Then take LR(1) closure.

### 14.5 CLR Table Construction

1. Augment grammar with `S' -> S`.
2. Start with closure of `[S' -> . S, $]`.
3. Compute GOTO sets for terminals and nonterminals.
4. For item `[A -> α . a β, b]`, add shift on terminal `a`.
5. For item `[A -> α ., a]`, add reduce by `A -> α` only under lookahead `a`.
6. For `[S' -> S ., $]`, add accept on `$`.
7. GOTO entries are added for nonterminal transitions.

### 14.6 CLR Example

Consider:

```text
S -> C C
C -> c C | d
```

Augmented:

```text
S' -> S
S  -> C C
C  -> c C
C  -> d
```

Initial item:

```text
[S' -> . S, $]
```

Closure:

```text
I0:
[S' -> . S, $]
[S  -> . C C, $]
[C  -> . c C, c]
[C  -> . d, c]
[C  -> . c C, d]
[C  -> . d, d]
```

Why lookahead `c` and `d` for `C`? In `[S -> . C C, $]`, the first `C` is followed by another `C`. Therefore the lookahead for the first `C` is FIRST(C), which is `{c, d}`.

After recognizing the first `C`, state contains:

```text
[S -> C . C, $]
[C -> . c C, $]
[C -> . d, $]
```

Now the second `C` is followed by `$`, so its lookahead is `$`.

This precision is why CLR is more powerful than SLR.

### 14.7 CLR Parsing of `c d d`

For:

```text
c d d $
```

the intended structure is:

```text
S -> C C
first C -> c C -> c d
second C -> d
```

Reduction sequence:

```text
c d d
=> c C d
=> C d
=> C C
=> S
```

A CLR parser performs these reductions only when the lookahead attached to the item permits them.

## 15. LALR(1) Parsing

### 15.1 Why LALR Exists

CLR(1) parsers are powerful but can create many states. Many states differ only in lookahead sets while having the same LR(0) core.

LALR(1) reduces table size by merging CLR states with identical LR(0) cores.

### 15.2 LR(0) Core

The core of an LR(1) item is the production with dot position, ignoring lookahead.

For:

```text
[A -> α . β, a]
```

the core is:

```text
A -> α . β
```

If two CLR states have the same set of cores, LALR merges them and unions the lookaheads.

### 15.3 LALR Construction

1. Construct CLR(1) item sets.
2. Identify states with identical LR(0) cores.
3. Merge such states by combining lookahead sets.
4. Construct ACTION and GOTO tables from merged states.
5. If merging introduces reduce-reduce conflicts, the grammar is not LALR(1).

### 15.4 Why LALR is Popular

LALR has nearly the power of CLR for many programming languages but table sizes close to SLR. This is why classic parser generators such as Yacc and Bison traditionally use LALR(1).

### 15.5 LALR Limitation

Merging states can introduce conflicts that did not exist in CLR. Therefore:

```text
CLR(1) is more powerful than LALR(1)
```

Every LALR(1) grammar is CLR(1), but not every CLR(1) grammar is LALR(1).

## 16. Operator Precedence Parsing

### 16.1 Simple Intuition

Operator precedence parsing is a bottom-up parsing technique for expressions. It uses precedence relations between terminals to decide when to shift and when to reduce.

The main relations are:

```text
a <. b   means a yields precedence to b
a =. b   means a has equal precedence with b
a .> b   means a takes precedence over b
```

Informally:

1. If stack-top terminal yields precedence to input terminal, shift.
2. If stack-top terminal takes precedence over input terminal, reduce.
3. Equal precedence often connects matching pairs like parentheses or operators in a handle.

### 16.2 Operator Grammar

An operator-precedence grammar should not have:

1. ε-productions.
2. Two adjacent nonterminals on the right-hand side.

Example:

```text
E -> E + E | E * E | id
```

This is an operator grammar because terminals separate nonterminals. It is ambiguous as a CFG, but operator precedence rules can disambiguate parsing decisions.

### 16.3 FIRSTVT and LASTVT

Many textbooks use FIRSTVT and LASTVT, sometimes called LEAD and LAST.

FIRSTVT(A) is the set of terminals that can appear first in some string derived from `A`, considering operator grammar structure.

LASTVT(A) is the set of terminals that can appear last in some string derived from `A`.

Rules for FIRSTVT:

1. If `A -> a ...`, add `a` to FIRSTVT(A).
2. If `A -> B a ...`, add `a` to FIRSTVT(A).
3. If `A -> B ...`, add FIRSTVT(B) to FIRSTVT(A).

Rules for LASTVT:

1. If `A -> ... a`, add `a` to LASTVT(A).
2. If `A -> ... a B`, add `a` to LASTVT(A).
3. If `A -> ... B`, add LASTVT(B) to LASTVT(A).

### 16.4 Precedence Table Rules

For each production:

1. If two terminals are adjacent, `a b`, set `a =. b`.
2. If terminals surround one nonterminal, `a B b`, set `a =. b`.
3. If terminal `a` appears before nonterminal `B`, set `a <. t` for all `t ∈ FIRSTVT(B)`.
4. If nonterminal `B` appears before terminal `a`, set `t .> a` for all `t ∈ LASTVT(B)`.
5. Add `$ <. t` for starting terminals and `t .> $` for ending terminals.

### 16.5 Example: `E -> E + E | E * E | id`

Terminals:

```text
id, +, *, $
```

Assume:

1. `*` has higher precedence than `+`.
2. Both are left associative.
3. `id` has highest precedence as operand.

Relations:

```text
$ <. id
$ <. +
$ <. *
id .> +
id .> *
id .> $
* .> +
+ <. *
+ .> $
* .> $
+ .> +
* .> *
```

For left associativity:

```text
+ .> +
* .> *
```

For multiplication higher than addition:

```text
+ <. *
* .> +
```

### 16.6 Parsing `2 + 3 * 4`

Treat numbers as `id`:

```text
id + id * id $
```

Trace:

```text
Stack        Input             Action
$            id + id * id $    $ <. id, shift
$ id         + id * id $       id .> +, reduce id to E
$ E          + id * id $       $ <. +, shift
$ E +        id * id $         + <. id, shift
$ E + id     * id $            id .> *, reduce id to E
$ E + E      * id $            + <. *, shift
$ E + E *    id $              * <. id, shift
$ E + E * id $                 id .> $, reduce id to E
$ E + E * E  $                 * .> $, reduce E * E to E
$ E + E      $                 + .> $, reduce E + E to E
$ E          $                 accept
```

The parser reduces multiplication before addition because `*` has higher precedence.

## 17. Relationship Among LL(1), LR(0), SLR(1), LALR(1), CLR(1), and LR(1)

### 17.1 Power Relationship

The usual inclusion relationship is:

```text
LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ CLR(1) = LR(1)
```

Also:

```text
LL(1) ⊂ LR(1)
```

That means every LL(1) grammar is LR(1), but not every LR(1) grammar is LL(1).

### 17.2 LL(1) vs LR(1)

LL(1):

1. Top-down.
2. Produces leftmost derivation.
3. Cannot handle left recursion.
4. Needs one-token predictive choice.
5. Easier to implement by hand.

LR(1):

1. Bottom-up.
2. Produces rightmost derivation in reverse.
3. Can handle left recursion.
4. More powerful.
5. More complex tables and construction.

### 17.3 LL(1) and LR(0) Are Incomparable

Two grammar classes are incomparable if neither completely contains the other.

There are grammars that are LL(1) but not LR(0), and grammars that are LR(0) but not LL(1).

Example of LL(1) but not LR(0):

```text
S -> A
A -> a | ε
```

This can be LL(1) if FOLLOW(A) is `$`, because `a` selects `A -> a` and `$` selects `A -> ε`. But LR(0) has difficulty because reductions by ε require lookahead. LR(0) cannot know whether to reduce `A -> ε` without seeing the next token.

Example of LR(0) but not LL(1):

```text
S -> S a | b
```

This grammar is left recursive, so it is not LL(1). However, some left-recursive grammars can be LR(0) because bottom-up parsers handle left recursion naturally.

## 18. Dangling Else and Predictive Parsing

### 18.1 The Problem

The classic grammar:

```text
S -> if E then S
   | if E then S else S
   | a
E -> b
```

is ambiguous. For:

```text
if b then if b then a else a
```

the `else` could attach to:

1. The inner `if`.
2. The outer `if`.

Most languages define that `else` attaches to the nearest unmatched `if`.

### 18.2 Left-Factored Grammar

Factored form:

```text
S  -> if E then S S' | a
S' -> else S | ε
E  -> b
```

This helps predictive parsing, but the grammar still creates an LL(1) conflict because `else` may be in FOLLOW(S') and also begins an alternative of `S'`.

### 18.3 Proper Unambiguous Grammar

A common unambiguous grammar separates matched and unmatched statements:

```text
S -> M | U
M -> if E then M else M | a
U -> if E then S | if E then M else U
E -> b
```

Here:

1. `M` means matched statement: every `if` has an `else`.
2. `U` means unmatched statement: there is an `if` without a matching `else`.

This grammar encodes nearest-else association.

## 19. Error Handling in Parsing

### 19.1 What Is an Error Handler?

An error handler is the part of a compiler that detects, reports, and tries to recover from errors in the source program.

A good error handler should:

1. Detect errors as early as possible.
2. Report meaningful messages.
3. Continue parsing after an error when possible.
4. Avoid producing many misleading follow-up errors.

### 19.2 Lexical Errors

Lexical errors occur during scanning.

Examples:

```text
@invalid
12.34.56
"unterminated string
```

These errors involve invalid characters or malformed tokens.

### 19.3 Syntax Errors

Syntax errors occur during parsing.

Examples:

```text
if (x > 0 {
x = + y;
while x) statement;
```

The tokens may be valid individually, but their arrangement violates grammar rules.

### 19.4 Error Recovery Techniques

Panic-mode recovery:

The parser skips input tokens until it finds a synchronizing token such as `;`, `}`, or `$`. This is simple and prevents infinite error loops.

Phrase-level recovery:

The parser locally inserts, deletes, or replaces tokens to continue.

Error productions:

The grammar includes common wrong patterns so the parser can produce specific messages.

Global correction:

The parser searches for the smallest set of changes that would make the input valid. This is theoretically interesting but usually too expensive for practical compilers.

### 19.5 Example

Input:

```text
x = y + ;
```

The parser expects an operand after `+`, such as `id` or `num`, but sees `;`.

A message could be:

```text
syntax error: expected expression after '+'
```

Then the parser may skip to `;` and continue parsing the next statement.

## 20. Exam-Oriented Answers

### 20.1 Ambiguous, Left Recursive, and Left Factoring Grammars

An ambiguous grammar is a grammar in which at least one string has more than one parse tree, or equivalently more than one leftmost or rightmost derivation. The problem with ambiguity is that it gives more than one syntactic interpretation to the same input. In programming languages this can change meaning. For example, `E -> E + E | E * E | id` is ambiguous for `id + id * id`. One parse means `id + (id * id)`, while another means `(id + id) * id`. To remove ambiguity, the grammar must encode precedence and associativity, such as `E -> E + T | T`, `T -> T * F | F`, `F -> id | (E)`.

A left-recursive grammar has a nonterminal that can derive itself as the leftmost symbol. Immediate left recursion has the form `A -> Aα | β`. This creates problems for top-down parsers because procedure `A()` may call itself before consuming input. For example, `E -> E - T | T` causes infinite recursion in recursive descent. It can be transformed into `E -> T E'`, `E' -> - T E' | ε`.

A left-factoring or non-deterministic grammar has alternatives with a common prefix, such as `A -> αβ1 | αβ2`. A predictive parser seeing `α` cannot choose which production to use. The solution is `A -> αA'`, `A' -> β1 | β2`. For example, `Stmt -> id = E | id ( Args )` becomes `Stmt -> id Stmt'`, `Stmt' -> = E | ( Args )`.

### 20.2 Steps to Create an LL(1) Parsing Table

To construct an LL(1) parsing table, first ensure the grammar is suitable for top-down parsing. Remove immediate and indirect left recursion because LL parsers cannot handle left-recursive grammars. Then apply left factoring so that alternatives of a nonterminal do not begin with the same prefix.

Next compute FIRST sets. FIRST of a symbol or string tells which terminals can begin strings derived from it. If a string can become empty, include ε. Then compute FOLLOW sets. FOLLOW of a nonterminal contains terminals that can appear immediately after that nonterminal in some sentential form. Add `$` to FOLLOW of the start symbol.

For every production `A -> α`, put the production in table entry `M[A,a]` for every terminal `a` in `FIRST(α)` except ε. If ε is in `FIRST(α)`, put `A -> α` in `M[A,b]` for every `b` in FOLLOW(A). After filling the table, inspect every cell. If any cell contains more than one production, the grammar is not LL(1). If every filled cell has at most one production, the grammar is LL(1).

### 20.3 LR(0) Algorithm Short Note

To construct LR(0) item sets, augment the grammar by adding `S' -> S`. Start with `closure(S' -> .S)`. The closure function adds productions for any nonterminal appearing immediately after a dot. If an item contains `A -> α . B β`, then for every production `B -> γ`, add `B -> .γ`. Repeat until no more items can be added.

The GOTO function moves the dot over a grammar symbol. If an item set contains `A -> α . X β`, then `GOTO(I, X)` includes `A -> α X . β`, followed by closure. By repeatedly applying GOTO to all item sets and grammar symbols, we obtain the canonical collection of LR(0) items.

The LR(0) parsing table is built from these item sets. Dot-before-terminal items create shift actions. Completed items create reduce actions under all terminals. The augmented completed item creates accept on `$`. Nonterminal transitions fill the GOTO table. If any cell contains conflicting actions, the grammar is not LR(0).

## 21. Final Study Strategy

To solve new parsing questions, follow a reliable method rather than memorizing examples.

For ambiguity:

1. Choose a suspicious string.
2. Try to draw two parse trees.
3. If two parse trees exist, grammar is ambiguous.
4. Remove ambiguity by encoding precedence, associativity, or matched/unmatched structure.

For left recursion:

1. Identify productions of the form `A -> Aα`.
2. Separate left-recursive alternatives from non-left-recursive alternatives.
3. Apply `A -> βA'`, `A' -> αA' | ε`.
4. Preserve every alternative.

For left factoring:

1. Look for common prefixes.
2. Pull the common prefix out.
3. Create a new nonterminal for the remaining suffix choices.

For LL(1):

1. Remove left recursion.
2. Left factor.
3. Compute FIRST.
4. Compute FOLLOW.
5. Fill table.
6. Check for conflicts.
7. Parse using stack, input, and table.

For LR parsing:

1. Augment grammar.
2. Build item sets using closure and GOTO.
3. Fill ACTION and GOTO.
4. Identify conflicts.
5. Parse by shift and reduce actions.

Parsing becomes manageable when every question is broken into these mechanical steps. The important skill is not remembering a finished table. The important skill is knowing what each symbol, dot, stack entry, lookahead, and table cell means.
